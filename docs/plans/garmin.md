# Garmin 数据采集方案

更新：2026-11-19。适用于Forerunner 265、中国区个人账号。官方取数、每日编排、严格N日回查、有限网络重试和看板已实现并部署云端；11月18日09:00首次自然采集、19日09:00含报告的自然执行通过，服务成功退出且日任务完成，独立证据见核验报告。停机补跑、超时恢复及长期运行继续验收。P4资格、证据和每晚唯一报告已实现；新报告链路的真实与自然触发验收见核验报告。
本文维护数据源与采集策略；[字段口径](../data-contract.md)、[操作步骤](../operations.md)和[实测结果](../verification.md)分别维护。

## 官方依据与能力边界

截至2026-11-10核验的[官方Swagger](https://developer.garmin.com/gc-developer-program/personal/swagger-docs/)为OpenAPI3.0.1、API1.0.0，包含中国区及国际区服务器。
[官方FAQ](https://developer.garmin.com/gc-developer-program/personal/personal-faq/)说明个人Key换取access token，token最长24小时且无refresh token；
[官方Python SDK](https://github.com/garmin/connect-personal-api-python)提供认证与GET封装。程序始终使用配置区域，认证失败不自动换区。

当前范围为睡眠、HRV、心率、活动、日汇总、压力、步数、SpO2、Body Battery及日常活动摘要。
可用字段及稀疏程度由真实响应核验，不因接口存在就假定字段齐全。当前官方数据没有睡眠分期起止区间，
也没有已接入的完整压力/独立呼吸时序、训练准备度、恢复时间或体动曲线。
观测频率和原文一致性不证明设备准确度；睡眠窗口及累计时长的展示见[看板方案](dashboard.md)。

Garmin Connect允许编辑已经记录的睡眠起止时间，因此不能把“已取得”理解为“以后绝不会改变”。官方操作说明见[Garmin Sleep Tracking：Adding or Editing Sleep Times](https://support.garmin.com/en-IN/?faq=mBRMf4ks7XAQ03qtsbI8J6)。本项目直接展示已有有效观测，同时保留后续补采、API有效修订和原始快照；取消当日“待确认”标签不改变这些数据保护规则。

## 常规采集资源

`garmin-collect`默认截至配置时区昨日，详细7日、背景31日。初始化7个睡眠日且要求每晚完整负荷基线时使用38日背景。

| 资源键 | 常规窗口与请求结构 |
| --- | --- |
| `sleep`、`hrv`、`daily`、`spo2` | 详细窗口逐日请求 |
| `heart_rate` | 详细窗口及首日前一天，覆盖跨午夜 |
| `daily_summaries` | 背景窗口，程序每块最多365日，响应为`data[]` |
| `sleep_summaries` | 背景窗口，每块最多31日 |
| `hrv_summaries` | 背景窗口，程序保守拆28日，响应为`hrvSummaries[]` |
| `stress`、`steps` | 背景窗口，每块最多28日 |
| `body_battery`、`wellness_activities` | 详细窗口的范围资源；Body Battery最多31日 |
| `activities` | 背景窗口每7日分块，每页100条，每块最多50页 |

活动使用`excludeChildren=true`。不足一页才完成；重复页、重复ID、无效ID或达到页数上限均拒绝声明完整。
7日活动分块源于整段查询故障后的实现选择，不是官方上限。分页审计行数与实际HTTP次数分别记录，token与重试另计。
Body Battery和SpO2未额外取首日前一天，首夜跨午夜可能有缺口；不通过填值掩盖来源缺失。

## 手动同步与今日采集

`garmin-sync`按配置时区今天生成计划，无`--end`参数；常规`garmin-collect`仍拒绝今天和未来截止日。

| 日期范围 | 资源与状态 |
| --- | --- |
| 可包含今天的详细窗口 | sleep、HRV、心率、SpO2、Body Battery、wellness；看板状态按实际观测，不按日期统一标pending |
| 已结束日期，最多到昨日 | daily、背景摘要、压力、步数和正式活动；不将今天的全天统计宣称完整 |

手动`garmin-sync`保留首次背景38日、滚动7日、距成功宽窗口满7日再查38日的策略。详细默认7个来源日，包含今天D，即D−6至D，心率额外补首日前一天。它是显式维护入口，日常定时改用下节的`daily-run`，两者不并行安装。
`--history-days`可显式调整本轮背景；既有历史保留，采集窗口不限制核验或负荷计算回读30日基线。看板可独立配置睡眠归属日起点，仅隐藏较早夜晚的展示入口，不修改采集窗口、保存范围或负荷背景，规则见[数据契约](../data-contract.md#看板睡眠日期展示边界)。
`verify`保留本轮覆盖统计，同时以`load_evaluation_window`单列读取存量历史与请求状态，今日全天负荷保持暂定。

仅整轮completed推进成功窗口。短停机扩大详细窗口至最多31日；超过30个已结束日未成功采集时，
返回`backfill_required`及分块补采命令并停止联网，执行成功后再sync。未执行补采不标记已补齐。
计划及请求审计继续记录完整日截止、暂定日期/资源和完成状态；这些采集覆盖字段不直接决定卡片标签，不修改原文来“确认”今日数据。看板兼容字段`is_provisional=false`不声明来源定稿，未结束全天负荷的独立限制见数据契约。

## 每天9点的统一编排（P5）

`SLEEPSCAPE_GARMIN_LOOKBACK_DAYS=7`已接入Settings，允许正整数1—31。用户所说“−7”对应含今天的D−6…D，而不是含今天再加7天。`daily-run`固定使用上海日期，睡眠/HRV详细及历史摘要都受同一N日边界约束；N=1时不请求窗口外的历史睡眠/HRV摘要，心率仅额外覆盖首日前一天。睡眠范围不因停机自动扩大。

负荷背景独立读取截至昨日的N+30个已结束日，支持窗口最早夜晚的昨日负荷及之前30自然日基线；默认N=7读取37日背景，N=31读取61日。该范围不是额外睡眠回查，也不能保证上游必然返回完整活动。分页、认证和有限网络重试会增加物理请求数，计划数不等于HTTP次数。

唯一日常触发为**每天09:00，Asia/Shanghai**。[定时模板](../../deploy/garmin-sync.timer)已在云服务器安装启用；`AccuracySec=1min`表示实际触发可在该精度窗口内发生，并非秒级承诺。11月18日首次自然触发已核验，服务09:00:08开始、09:00:46成功退出，日任务账本为completed，当次报告尚未启用；停机补运行、超时恢复和长期调度另验。完整证据见[核验报告](../verification.md)。
保留`Persistent=true`：服务停机后恢复时可补一次错过的触发，不会按错过天数逐次回放；恢复时仍只按当前上海日的N日窗口执行。服务名保留`garmin-sync.service`，唯一ExecStart已改为`sleepscape daily-run`，不新增第二套每日定时器。
设备必须先同步到Garmin Connect；服务器不能代替手表与手机的同步，也不为了晚同步另加12:30的日常任务。

以默认N=7、2026-11-17为例，9点请求11/11至11/17的睡眠来源日，11/17通常对应11/16晚至11/17早的主睡眠，仍以API返回的真实起止和来源日为准。
若11/17早尚未同步，11/18的9点任务会请求11/12至11/18，因此可补到11/17的晚到记录。当天9点尚未醒、尚无有效睡眠窗口或API尚未给出数据时，保留实际缺失/无效原因，不能自行判定睡眠结束、填0或沿用上一夜冒充当夜；已有有效观测可先展示。

两种缺口分别处理：

- **手表晚同步**：请求成功仍可能得到空数据；日任务可为completed，但对应来源日仍显示缺失，次日窗口内再取。不即时轮询。N=1不会在次日自动补昨日；需要补晚到数据应配置N≥2，默认7。越出窗口的日期只能显式执行日期补采。
- **服务器采集停机/失败**：下一次触发仍执行当前N日，不因漏跑扩大睡眠范围；窗口外缺口保留，需人工指定`garmin-collect`日期和范围处理。手动`garmin-sync`的扩窗规则不用于P5。

同一上海日的已记录终态默认不重复联网；显式`daily-run --retry`仅重试partial/failed/interrupted/deferred，completed即使缺睡眠也不会重跑。显式历史补采仍是独立维护行为。编排和手动采集共用进程锁，网络等待不持SQLite写事务；崩溃后对照已落库的运行结果恢复，避免已完成轮次再次拉取。长Retry-After跨命令保留，显式重试也不能绕过。

私有有界运行元数据与SQLite事实分离保存。看板分别展示任务状态、计划/完成/失败请求计数、延后时间及逐日睡眠观测状态，不将HTTP成功写成数据齐全；只读刷新不联网、不修复账本、不触发分析。状态合同与迁移规则分别见[数据契约](../data-contract.md)和[运行操作](../operations.md)。

HTTP200、整轮`completed`或来源日期已过去，都不证明设备同步完整。今日有效观测直接展示，过午夜本身不改变卡片可用性；后续回查及有效修订继续更新当前事实并保留原始证据。P4第一步按实际闭合窗口及双源门槛判定，不能凭日期或兼容的`is_provisional`字段阻塞或放行；独立analysis-check仅检查；daily-run在自动分析开启后可继续生成未发布报告。

### 与完整性检查和LLM睡眠分析的衔接

数据选择、Prompt、输出与预算由[LLM方案](llm.md)维护。P4已实现：09:00采集返回并释放采集锁后，本地检查相同N日，再按独立自动开关调用已具备资格且尚未发布的报告用例。
检查复用已有Garmin与原始环境投影，不重新联网、不补0。硬件全天主动上传，09:00不向设备拉取不存在的数据。当前分析门槛见数据契约；未采到的旧数据不能补造，自动任务仅为尚未发布的夜晚生成首份报告。
模型失败不回滚Garmin采集或阻塞环境上传。调用不进入`services.collection`、Garmin适配器、数据库方法或看板GET；采集锁只约束Garmin，分析使用独立身份/锁，读取一致快照后先释放数据库事务再外呼。

## 采集保护与失败行为

- 路径及参数白名单，仅访问已纳入计划的官方资源；不额外查询profile、FIT、GPS轨迹或其他个人资料接口。
- 单响应读取上限10MiB，GET间隔至少0.2秒，文件排他锁阻止两轮采集同时执行。
- 每个数据请求遇临时连接/读取/分块传输错误或429、500/502/503/504时，累计暂时失败最多3次（通常初次加2次重试），默认等待1秒、2秒；SDK读取超时20秒。401另允许整轮最多一次token刷新并重发，不计入上述暂时失败额度；token获取本身亦有界最多3次尝试。因此不能把“3次”误称包括所有认证往返的总HTTP次数。403、重复401、非暂时4xx或结构错误不无限重试。
- 请求成功但没有睡眠数据属于等待手表同步，不按网络故障立即重复请求；缺项在看板保留，次日09:00按配置窗口回查。网络重试耗尽记录失败/陈旧状态并结束该资源或本轮保护流程，日常编排不再额外套一层整轮重试。
- `Retry-After`不超过10秒可等待；更长则记`retry_not_before`并停轮，下一任务遵守等待。认证失败或限流耗尽停止整轮。
- 单资源失败可保留已有记录并继续其他资源；无效响应不清空原分区，视图与报告标记陈旧风险。
- 有效空响应与请求失败分开：有效空响应记`empty`并可清空对应当前标准化分区，不能解释为睡眠时长0；请求失败或无效结构保留已有事实并标陈旧。有效修订原子替换当前来源分区，原始快照保留修订证据。

原始快照按`(resource, request_key, content_hash)`去重；当前记录按`(resource, kind, record_key)`定位。
滚动窗口改变请求键时仍可能新增原始快照，不能称为全局跨窗口去重。重复来源分开保存，不重复合计指标。
密钥/token只由适配器读取；终端仅输出安全状态、数量和问题码，不输出完整响应或凭据。

## 核验责任

`garmin-verify`离线检查原始字段、标准化、来源日期、单位、时序和显示数据前提；负荷公式只采用数据契约中的固定口径。
`garmin-audit`只读源库，在私有临时库重放两遍，核对raw哈希、JSON、去重与当前记录；故障/修订/回滚用合成场景另验。
临时库结束后清理，报告覆盖写入当前文件，原始观测与审计继续保留。
采集已完成、数据转换一致、浏览器已验收、云端持续运行和手表测量准确度分别记录，不相互替代。

环境采集、时间查询和共轴看板已建立独立来源，详情见[硬件方案](hardware.md)。它们不改变Garmin的区域、认证、日期或字段口径；真实采集时间与本轮文档整理分别记录在核验报告。
