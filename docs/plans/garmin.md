# Garmin 数据采集方案

更新：2026-11-17。适用于Forerunner 265、中国区个人账号。
本文维护数据源与采集策略；[字段口径](../data-contract.md)、[操作步骤](../operations.md)和[实测结果](../verification.md)分别维护。

## 官方依据与能力边界

截至2026-11-10核验的[官方Swagger](https://developer.garmin.com/gc-developer-program/personal/swagger-docs/)为OpenAPI3.0.1、API1.0.0，包含中国区及国际区服务器。
[官方FAQ](https://developer.garmin.com/gc-developer-program/personal/personal-faq/)说明个人Key换取access token，token最长24小时且无refresh token；
[官方Python SDK](https://github.com/garmin/connect-personal-api-python)提供认证与GET封装。程序始终使用配置区域，认证失败不自动换区。

当前范围为睡眠、HRV、心率、活动、日汇总、压力、步数、SpO2、Body Battery及日常活动摘要。
可用字段及稀疏程度由真实响应核验，不因接口存在就假定字段齐全。当前官方数据没有睡眠分期起止区间，
也没有已接入的完整压力/独立呼吸时序、训练准备度、恢复时间或体动曲线。
观测频率和原文一致性不证明设备准确度；睡眠窗口及累计时长的展示见[看板方案](dashboard.md)。

## 常规采集资源

`garmin-collect`默认截至配置时区昨日，详细7日、背景31日。初始化7个睡眠日且要求每晚完整负荷基线时使用38日背景。

| 资源键 | 常规窗口与请求结构 |
| --- | --- |
| `sleep`、`hrv`、`daily`、`spo2` | 详细窗口逐日请求 |
| `heart_rate` | 详细窗口及首日前一天，覆盖跨午夜 |
| `daily_summaries` | 背景窗口，程序每块最多365日，响应为`data[]` |
| `sleep_summaries` | 背景窗口，每块最多31日 |
| `hrv_summaries` | 背景窗口，程序保守拆28日，响应为`hrvSummaries[]` |
| `stress`、`steps` | 背景窗口，每块最多28日 |
| `body_battery`、`wellness_activities` | 详细窗口的范围资源；Body Battery最多31日 |
| `activities` | 背景窗口每7日分块，每页100条，每块最多50页 |

活动使用`excludeChildren=true`。不足一页才完成；重复页、重复ID、无效ID或达到页数上限均拒绝声明完整。
7日活动分块源于整段查询故障后的实现选择，不是官方上限。分页审计行数与实际HTTP次数分别记录，token与重试另计。
Body Battery和SpO2未额外取首日前一天，首夜跨午夜可能有缺口；不通过填值掩盖来源缺失。

## 今日暂定与滚动同步

`garmin-sync`按配置时区今天生成计划，无`--end`参数；常规`garmin-collect`仍拒绝今天和未来截止日。

| 日期范围 | 资源与状态 |
| --- | --- |
| 可包含今天的详细窗口 | sleep、HRV、心率、SpO2、Body Battery、wellness；今日数据标pending/is_provisional |
| 已结束日期，最多到昨日 | daily、背景摘要、压力、步数和正式活动；不将今天的全天统计宣称完整 |

当前实现的同步策略：首次背景38日；日常回查7日；距成功宽窗口满7日再查38日。详细默认7个来源日，**包含今天D，即D−6至D**，心率额外补首日前一天。
计划新增`SLEEPSCAPE_GARMIN_LOOKBACK_DAYS=7`，将日常回查窗口配置为正整数N，并复用现有`detail_days`参数及其1—31范围校验。用户所说“−7”表示向前回查最近7个睡眠来源日，配置实际写`7`，范围为D−(N−1)至D；不是含今天再加7天。该配置项与每日编排的连接**尚未实现**，当前CLI仍可显式使用`garmin-sync --detail-days N`。
停机恢复可以沿用`prepare_sync`扩大实际取数窗口的逻辑；LLM候选夜晚仍按本次配置窗口筛选，窗口外未分析记录需显式扩大窗口或指定补采后再评估。
`--history-days`可显式调整本轮背景；既有历史保留，采集窗口不限制展示或核验回读30日基线。
`verify`保留本轮覆盖统计，同时以`load_evaluation_window`单列读取存量历史与请求状态，今日全天负荷保持暂定。

仅整轮completed推进成功窗口。短停机扩大详细窗口至最多31日；超过30个已结束日未成功采集时，
返回`backfill_required`及分块补采命令并停止联网，执行成功后再sync。未执行补采不标记已补齐。
计划及请求审计记录完整日截止、暂定日期/资源和完成状态，不修改原文来“确认”今日数据。

### 每天9点、晚到数据与补采

用户已确定唯一日常触发为**每天09:00，Asia/Shanghai**。已同步[定时模板](../../deploy/garmin-sync.timer)，仍未在云服务器安装；`AccuracySec=1min`表示实际触发可在该精度窗口内发生，并非秒级承诺。
保留`Persistent=true`：服务停机后恢复时可补一次错过的触发，不会按错过天数逐次回放；历史范围仍由`prepare_sync`判断。
设备必须先同步到Garmin Connect；服务器不能代替手表与手机的同步，也不为了晚同步另加12:30的日常任务。

以默认N=7、2026-11-17为例，9点请求11/11至11/17的睡眠来源日，11/17通常对应11/16晚至11/17早的主睡眠，仍以API返回的真实起止和来源日为准。
若11/17早尚未同步，11/18的9点任务会请求11/12至11/18，因此可补到11/17的晚到记录。当天9点尚未醒、尚无有效睡眠窗口或API尚未给出数据时，保持缺失/暂定状态，不能自行判定睡眠结束、填0或沿用上一夜冒充当夜。

两种缺口分别处理：

- **手表晚同步**：服务器每天请求成功仍可能得到空数据，成功窗口不是“每一晚已有观测”的证明。晚到记录仍在配置窗口内时由重叠回查取得；默认N=7时，延迟达到7天或更久的详细记录可能已超出窗口，应显示缺失并执行显式日期补采。每周38日背景可能取得部分摘要，但不能替代已遗漏的详细序列。
- **服务器采集停机/失败**：沿用上文基于最近成功窗口的补采机制；超过30个已结束日时进入`backfill_required`，先按分段计划补采再恢复日常sync。

HTTP200、整轮`completed`或来源日期已过去，都不证明设备同步完整。今日可用记录保持`is_provisional`，后续日期的回查及修订更新事实，不能只因过了午夜便推断数据质量改善。该今日标签本身也不是LLM的一票否决条件：若睡眠确已结束且双源必需数据满足合同，可首次生成；尚未结束或必需字段缺失则等待。

### 与LLM睡眠分析的衔接（待实现）

用户新增第一版LLM睡眠分析，详细数据选择、Prompt、输出和成本边界由[LLM方案](llm.md)统一维护。
目标为每天9点按配置窗口回查Garmin并核对已接收、待补齐的硬件记录，再由独立服务串行执行输入准备、完整性判定、模型调用及结果保存。硬件仍全天主动上传，9点不会让服务器直接向设备拉取不存在的数据；服务器仅能接收设备补传并复查库中结果。
**仅在Garmin与硬件两者的必需数据齐全时，才首次送LLM；每晚最多成功发布一份报告。** 缺项时看板逐项列出原因，不发送不完整输入、不发布partial报告。具体必需字段、时间/覆盖要求和状态合同由[LLM方案](llm.md)及[数据契约](../data-contract.md)维护。
LLM失败可以按方案重试，但失败尝试不计为成功报告，不回滚Garmin采集，也不阻塞环境上传。当前定时模板仍调用已有`garmin-sync`，上述双源完整性检查与报告流程尚未实现。
不能把模型调用塞进`services.collection`、Garmin适配器、数据库方法或看板GET请求。采集文件锁仅约束Garmin采集；新增分析使用独立任务身份/锁，读取一致快照后释放数据库事务，再进行外部模型请求。
输入指纹用于保证快照一致和成功发布唯一性，不用于已发布报告的自动再生成：

- 生成中Garmin修订、有效空响应、环境补传或时间映射修正导致事实变化时，废弃尚未发布的候选结果，等待次日以新快照重新检查并尝试；不发布过期候选。
- 报告成功发布后，后续事实变化仅标记`source_changed`并保留原报告及其证据版本，不自动重跑或覆盖；Prompt、模型配置等变化也不自动重新分析该夜。
- 到配置回查窗口外仍未齐全的夜晚，标记`expired_unanalyzed`并保留数据及缺项，不自动扩大窗口无限追补；用户显式扩大窗口或执行指定日期补采后，对尚无成功报告的夜晚重新检查完整性并尝试。

## 采集保护与失败行为

- 路径及参数白名单，仅访问已纳入计划的官方资源；不额外查询profile、FIT、GPS轨迹或其他个人资料接口。
- 单响应读取上限10MiB，GET间隔至少0.2秒，文件排他锁阻止两轮采集同时执行。
- 每个数据请求遇临时连接/读取/分块传输错误或429、500/502/503/504时，累计暂时失败最多3次（通常初次加2次重试），默认等待1秒、2秒；SDK读取超时20秒。401另允许整轮最多一次token刷新并重发，不计入上述暂时失败额度；token获取本身亦有界最多3次尝试。因此不能把“3次”误称包括所有认证往返的总HTTP次数。403、重复401、非暂时4xx或结构错误不无限重试。
- 请求成功但没有睡眠数据属于等待手表同步，不按网络故障立即重复请求；缺项在看板保留，次日09:00按配置窗口回查。网络重试耗尽记录失败/陈旧状态并结束该资源或本轮保护流程，日常编排不再额外套一层整轮重试。
- `Retry-After`不超过10秒可等待；更长则记`retry_not_before`并停轮，下一任务遵守等待。认证失败或限流耗尽停止整轮。
- 单资源失败可保留已有记录并继续其他资源；无效响应不清空原分区，视图与报告标记陈旧风险。
- 有效空响应与请求失败分开：有效空响应记`empty`并可清空对应当前标准化分区，不能解释为睡眠时长0；请求失败或无效结构保留已有事实并标陈旧。有效修订原子替换当前来源分区，原始快照保留修订证据。

原始快照按`(resource, request_key, content_hash)`去重；当前记录按`(resource, kind, record_key)`定位。
滚动窗口改变请求键时仍可能新增原始快照，不能称为全局跨窗口去重。重复来源分开保存，不重复合计指标。
密钥/token只由适配器读取；终端仅输出安全状态、数量和问题码，不输出完整响应或凭据。

## 核验责任

`garmin-verify`离线检查原始字段、标准化、来源日期、单位、时序和显示数据前提；负荷公式只采用数据契约中的固定口径。
`garmin-audit`只读源库，在私有临时库重放两遍，核对raw哈希、JSON、去重与当前记录；故障/修订/回滚用合成场景另验。
临时库结束后清理，报告覆盖写入当前文件，原始观测与审计继续保留。
采集已完成、数据转换一致、浏览器已验收、云端持续运行和手表测量准确度分别记录，不相互替代。

环境采集已建立独立设备写入口和环境存储，详情见[硬件方案](hardware.md)。它不改本方案的区域、认证、日期或字段口径；本次方案核对只执行离线计划核验，没有触发真实Garmin请求。
