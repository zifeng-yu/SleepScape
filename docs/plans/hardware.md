## 决策

用户已确认主方案为 **M5Stack ATOM Voice / ATOM Echo C008-C + DFRobot Gravity AHT20 SEN0528 + VEML7700 SEN0228 + I²C分线模块DFR0759**。
主控已集成麦克风、USB接口与外壳；两块传感器用各自附带的Gravity线接入分线模块，分线模块附线通过四根公对公杜邦跳线接主控底部。全部共用3.3V、SDA21/SCL25的一条总线。
不焊接、不剥线、不缠绕裸线，不需要面包板、单独声卡或额外Grove线。四根跳线按标签逐一核对；分线模块提供固定插位，不在同一主控插孔塞两根线。

## 为什么先采这些数据

研究支持温热环境、声音和光照与睡眠有关，但无法给出适用于所有人的“影响最大前三名”。以下是证据、成本与可测性的综合选择。

| 观测 | 原始研究及适用边界 | 本项目用途 |
| --- | --- | --- |
| 温度与相对湿度 | [Okamoto-Mizuno 1999](https://pubmed.ncbi.nlm.nih.gov/10505822/)：7名健康年轻男性，在不同温湿组合下作睡眠测量；热且潮湿条件影响睡眠。样本小、部分条件极端，不代表个人最佳温度 | 一起记录，观察整晚水平和变化，不以湿度单独作因果判断 |
| 相对声音与事件 | [Basner 2011](https://pmc.ncbi.nlm.nih.gov/articles/PMC3001788/)：72人、多夜交通噪声实验，声音事件可伴随觉醒和心脏反应；来源、次数及适应有影响 | 保留分钟能量及较响事件时间，不仅存整夜均值 |
| 光照 | [Mason 2022](https://pmc.ncbi.nlm.nih.gov/articles/PMC8944904/)：20人、100 lx与昏暗条件的实验，观察到心率/HRV等改变；不能推断每种微弱夜灯的效果 | 识别开灯、较明显夜灯和亮度变化 |
| 通风/CO₂，后续可选 | [Strøm-Tejsen 2016](https://onlinelibrary.wiley.com/doi/full/10.1111/ina.12254)：卧室通风干预，CO₂与其他空气因素同时变化，不能当作纯CO₂因果实验 | 预算允许后增加真正CO₂传感器；第一版省略，不用VOC计算的eCO₂冒充 |

Garmin评分、分期和HRV也有误差。声音可能由醒来产生，开灯可能发生在觉醒之后；同一时间轴用于观察，不自动判因果。
后续分析宜同时看总睡眠/觉醒、睡眠均心率、夜间HRV、主观恢复，并保留运动负荷、压力及未测的咖啡因/酒精等混杂因素。
第一版衡量的是可用夜数、逐通道覆盖率、校时质量、缺口、故障恢复与数据一致性，不输出影响排名。

**主控USB口的5V与传感器总线的3.3V是不同位置，不能混接。** 两块传感器的接口侧上拉都跟随外部VCC；
统一从主控底部3V3给分线模块供电，才能使ESP32数据线保持3.3V电平。分线模块本身不降压，不能接主控5V孔或Grove口后再把它当3.3V总线。
两块模块已有上拉，当前短线100kHz设计不另加电阻；并联上拉、连接可靠性和长线影响仍需实物验收。
分线模块提供的是同一总线的多个插位，不能解决同地址冲突；以后扩展必须重新核对电压、地址、上拉及线长。
收到其他SKU、板卡修订或不同接口排列时，先核对官方资料与实物，不能直接沿用接线通电。

### 接线步骤

准备主控、两块传感器、分线模块、三根随模块附带的Gravity-4P线和四根公对公杜邦跳线。各Gravity线一端为整块插头，另一端为四个母端；只使用已经焊好接口的原厂模块。

```text
电脑USB-C → 支持数据的C公/A母转接头 → USB-A/C数据线 → C008-C
                                                        │ 内置麦克风
主控底部 3V3 / GND / G21 / G25
             │ 四根公对公跳线
             ▼
      DFR0759附带Gravity线
             ▼
      DFR0759分线模块（整条总线3.3V）
             ├─ 一组四针 ← SEN0528附线 ← AHT20温湿度
             └─ 一组四针 ← SEN0228附线 ← VEML7700光照

初次刷写/配置完成后：拔离电脑，将USB-A端接5V墙上电源。
```

1. **先拔掉主控USB，整套断电。** 将DFR0759附带线的整块插头插入分线模块白色接口；按插头卡口方向插到底，不强行反插。
2. 将这根线的四个母端分别接一根公对公跳线；跳线另一端按下表插入主控底部排母。先确认主控丝印再插，不按照片左右方向猜位置。
3. AHT20附线的整块插头接传感器，四个母端插到分线模块同一组的VCC、GND、SDA、SCL；VEML7700用自己的附线接另一组。这里不再加公对公跳线。
4. 逐根沿实物标签核对电源与信号，不能只按红黑蓝绿等颜色。主控和两块传感器必须共地；**VCC对应3V3、D/SDA对应G21、C/SCL对应G25**。确认没有错位一针、裸针互碰或松动。
5. 将模块固定在绝缘底板上，避开金属裸面；确认无误后才接USB数据线刷写。分线模块剩余空针保持不接，主控侧面的Grove口在本方案中也不接线。

| 分线模块附线所对应标签 | 主控底部插孔标签 | 用途 |
| --- | --- | --- |
| + / VCC | **3V3** | 两块传感器和分线模块的电源，不能接5V |
| − / GND | G / GND | 共地 |
| D / SDA | G21 | 共享数据线 |
| C / SCL | G25 | 共享时钟线 |

分线模块上每一组四针均使用同样的VCC/GND/SDA/SCL信号。若实物无清晰标签或附线端头与说明不符，保持断电核对商品和原厂图，不剪线、剥线或改接碰运气。
接稳后用绝缘底板/扎带固定，不遮住传感器开孔。温湿度模块与主控/充电器至少约20cm分开，避开被褥、人体呼气和空调直吹；
传感器附线决定可用距离，主控到分线模块的跳线保持短。光照模块固定朝向并记录位置，不能用不透明胶带遮住感光元件。
主控和麦克风靠近床边但不放枕下；换摆位记录新的placement配置。灯光、声音、热量来自不同位置时保留此限制。
本次核对的两块传感器官方原理图未列LED，分线模块原厂正反面图也未见指示灯；主控RGB由固件主动关闭。到货后仍须在暗室检查整套设备和墙上电源的实际自发光，保持光照感光窗、温湿度通风口和麦克风孔开放。

## 可测范围与不可承诺的精度

- AHT20的典型温度误差约±0.3℃、湿度约±2%RH仅适用于相应条件，不能延伸为全量程整机精度；官方驱动说明也给出随量程变大的误差。第一批到货做同位置热稳定和参考表对照，保留原值与单独偏置配置，不覆盖原始观测。
- VEML7700优先观察卧室弱光与亮灯变化。当前固定弱光档、每秒读取，名义量化步长约0.0084 lx/count；这不是绝对准确度，也不保证区分极暗夜灯。当前固定档的有效上限约550 lx，白天强光可能饱和，饱和标无效而不自动换档。0读数不证明完全无光，低光阈值只是工程质量提示。精确档位、换算、上限与预热规则统一见[数据契约](../data-contract.md#当前光照测量配置)。
  商品页所列0–120 klx及旧资料0.0036 lx/count不能作为本固件能力；换算采用[Vishay手册Rev.1.8](https://www.vishay.com/docs/84286/veml7700.pdf)与[2025-03-06应用说明](https://www.vishay.com/docs/84323/designingveml7700.pdf)，需要到货做遮光、亮灯、固定距离和对照表检查。
- 主控内置SPM1423麦克风，原厂SNR典型61.5dBA、灵敏度有±3dB公差；由94−61.5估算等效本底约32.5dBA仅供选型参考。第一版记录**固定配置下的相对dBFS**，不提供校准dBA，不保证区分20/25/30dBA安静卧室，也不据此判断专业噪声限值。[Knowles手册](https://m5stack.oss-cn-shenzhen.aliyuncs.com/resource/docs/datasheet/core/SPM1423HM4H-B_datasheet_en.pdf)
- 1秒RMS能反映相应时间尺度的响声；短促声音可能被稀释。字段必须称最大1秒RMS，不能称瞬时峰值声压。后续如需125ms事件，修改测量配置版本并重新验收。
- 不识别语言、鼾声或呼吸暂停，不保存/上传录音。关闭扬声器、语音服务、蓝牙音频、AGC和夜间RGB灯；音频RAM不得进入Flash core dump、调试日志或串口输出。

## 固件分层与资源选择

已建立单一`firmware/`工程。SDK固定为**ESP-IDF v5.5.6**，Git提交
`880a203ae603d08a94d06aa01e0d6761958e5e9e`；工具核验提交、工作树及子模块，工具链只安装在项目`.firmware-tools/`。
复用项目Python 3.12对应的基础解释器，SDK依赖使用独立虚拟环境，不修改系统Python，不引入Arduino、M5图形或语音框架。
CMake 3.30.2与Ninja 1.12.1也通过锁定SDK的官方工具清单安装并校验，不要求新手另外安装Homebrew。
传感器命令和I²S/PDM驱动直接由本项目实现；保留源码、依赖版本与可重复构建入口，不把可再生二进制当唯一交付物。

正常采集24小时，便于获得非睡眠时段对照，避免依赖尚未到达的Garmin睡眠窗口。夜间筛选由服务器完成。
温湿度每10秒、光照每1秒；声音16kHz单声道16bit流式采样，在RAM分块计算1秒RMS，每60秒输出汇总；每5分钟HTTPS批量上传。
这些频率是工程取舍，非研究认定的最佳频率。详细字段、空值、事件门槛及计数只在数据契约维护。

PDM配置为16kHz PCM、16S降采样，时钟2.048MHz，处于SPM1423的1–3.25MHz范围；取右声道。
[M5Unified官方板卡配置](https://github.com/m5stack/M5Unified/blob/master/src/M5Unified.inl)确认AtomVoice的GPIO23/33，
[官方麦克风默认配置](https://github.com/m5stack/M5Unified/blob/master/src/utility/Mic_Class.hpp)采用右声道；这属于资料交叉核验，仍需实物发声验证。
PCM按块在RAM处理，不保存整晚音频。
已启用I²S IRAM-safe并记录DMA溢出、裁剪和逐秒有效覆盖；音频、汇总/Flash、网络独立任务。
这不保证真实设备永不丢样；Flash擦写、TLS握手、重连同时发生的8小时压力验收仍需样机。
[Espressif I²S文档](https://docs.espressif.com/projects/esp-idf/en/v5.5.6/esp32/api-reference/peripherals/i2s.html)及本地锁定SDK为接口依据。

4MB Flash已固定单应用2MiB、队列文件系统1.5MiB、独立NVS及启动区域；**第一版USB升级，不承诺双分区OTA**。
构建工具强制应用镜像不超过1.8MiB；实际编译大小见核验报告。TLS与连续采样同时运行时最小空闲堆目标≥64KiB，无复位/看门狗异常。
这些是验收门槛，尚不是测试结果。若完整功能装不下，先裁掉多余框架/调试功能，不能静默牺牲采样、认证或时间质量；
仍不满足时提交更大主控的差价和修改范围让用户决定，不改服务器事实和上传协议来迁就板卡。

## 断网、掉电与时间

持续供电时目标缓存48小时，不承诺无电也能采集。无电池RTC，冷启动无网时只有boot_id和单调时间；UTC为空。
收到可靠SNTP锚点后，只对同一boot中的记录估算UTC并标误差/估计状态，不能用服务器收到时间冒充测量时间。
锚点与原始记录分离；时钟跳变不重分桶、不改已上传载荷；未知UTC不上Garmin精确时间轴。

本地采用固定长度二进制记录，JSON仅在上传时生成。分钟192B、合并事件64B、状态64B、时间锚点48B，
每条另有20B队列封装；每128条一个192B段头，同一设备换boot/测量配置时强制换段。元数据使用两份CRC校验副本。
正常连续48小时且每分钟都有一个合并事件的模型为：

`2880×(192+20+64+20) + 576×(64+20) + 48×(48+20) + 50×192 = 913,728 B`

另计192B双份元数据；活跃队列上限1MiB，拒收记录隔离区上限64KiB，文件系统分区1.5MiB。
[核验报告](../verification.md)记录实际编码与主机48小时测试占用；模型不等同SPIFFS实机写入/磨损验收。
重启/配置变更会增加段头，异常频繁重启和额外锚点不承诺仍保留完整48小时；空间满时按明确策略淘汰并保留丢失计数。
SPIFFS可靠可用量约75%，接近容量上限的GC可持续数秒；留空余不等于实时性保证。[官方存储说明](https://docs.espressif.com/projects/esp-idf/en/stable/esp32/api-reference/storage/spiffs.html)

循环分段、顺序追加、CRC识别损坏尾部，不能每秒擦写Flash；每个已完成分钟持久化一次，异常掉电可能丢尚未完成/提交的窗口。
ACK仅在服务器事务提交后发出，设备再释放相应记录；重发幂等，乱序ACK不能跳过未接收记录。
缓存满时淘汰最老未确认记录并持久化缺口/丢弃计数；事件和诊断日志限额，不能无限增长或填满分钟保底区。
上传失败采用指数退避和抖动；429遵守整数秒Retry-After（最长一天）；401/403保留数据、报告认证拒绝并延长重试，重新USB配置后恢复。
Wi-Fi独立以1–300秒重连退避。HTTPS使用官方CA包和主机名校验，不自动跟随重定向，不携带Garmin Key；
响应体上限4096B，失败/不完整响应不释放队列。未取得SNTP时间时只缓存，不关闭TLS校验。

## 新手实际操作与交付边界

已经提供适用当前macOS开发环境的统一工具`tools/firmware.py`，无需安装IDE或修改C代码：

1. 开发端运行`make firmware-setup`、`make firmware-build`和`make firmware-check`，得到针对C008-C的镜像；采购前已实现这些入口，结果见核验报告。
2. 到货断电后按本页步骤连接分线模块和传感器；用支持数据的USB-C公/USB-A母转接头及USB-A/C线连接Mac，明确选定`/dev/cu.…`串口，不能猜测或自动刷写任意设备。
3. 全新板首次安装执行`make firmware-first-flash PORT=/dev/cu.实际串口`；工具先核对SDK、地址与镜像大小，提示后需手动输入`FIRST-INSTALL`，才整片清除厂商固件、配置及全部数据，再以115200波特率写入SleepScape。这样为NVS和SPIFFS提供明确的初始状态；随后运行`make firmware-status PORT=/dev/cu.实际串口`，预期`status=ready`、`firmware_version=0.2.0`、`configured=false`。首装实机仍待验收。
4. 服务器先登记设备和测量配置，生成独立令牌到权限600、目录700的私有文件。运行`make firmware-configure PORT=/dev/cu.实际串口`交互输入设备ID、配置ID、Wi-Fi及完整HTTPS上传地址；密码和令牌隐藏输入。
5. 无需显示令牌的替代入口为`uv run --locked python tools/firmware.py configure --port /dev/cu.实际串口 --token-file 私有令牌文件`；也支持权限600、目录700的完整私有JSON配置文件。
6. 工具经USB发送单行JSON，仅收到设备“配置已写入NVS”的ACK才报成功；设备重启。再运行`make firmware-status PORT=/dev/cu.实际串口`，应为版本0.2.0、`configured=true`。这只说明有效配置已保存，不证明Wi-Fi、TLS或上传成功；必须另核首次真实传感器读数、时间锚点与服务器接收，再改接墙上电源并固定摆位。

普通升级使用`make firmware-flash PORT=/dev/cu.实际串口`，仅写启动程序、分区表与应用，保留NVS和离线队列；不得反复用首次安装命令升级或排障。操作细节统一见[运行手册](../operations.md#首次安装与后续升级)。

上传地址须为`https://你的域名/api/v1/ingest/environment-batches`，不能填写Garmin API地址、普通HTTP、查询参数或含用户名密码的URL。
PC配置工具不把秘密放命令行参数/环境变量，不回显USB载荷；无可隐藏输入的终端时拒绝回显降级，使用私有文件。
设备ID/配置ID使用字母、数字、点、短横线和下划线，首字符为字母或数字；Wi-Fi是2.4GHz，密码支持空或8–63字节。
换Wi-Fi可再次USB配置，无需重刷程序；普通NVS不宣称可抵抗物理读取。整片清除仅存在于需交互确认的独立首次安装流程，普通刷写和配置不会自动清除。

USB驱动兼容、自动下载及可能需要的按键步骤须到货后按实际电脑验证。[官方USB说明](https://docs.m5stack.com/en/arduino/m5atomecho/program)
首装20–40分钟只是操作估计，驱动或路由器问题可能更久；尚不能标“新手实操通过”。厂商语音固件不能代替SleepScape固件。

## 服务器与看板衔接

仍使用现有FastAPI单worker、SQLite WAL及可选Caddy，不增加MQTT、Redis、InfluxDB或常驻Node。
设备通过HTTPS主动上传，不要求家庭公网IP、路由器端口转发或云端连接家庭设备。

已为**精确的`POST /api/v1/ingest/environment-batches`路径**增加独立设备认证、体积/频率限制和事务接收；
其余页面和API继续现有访问保护，不能简单放开所有POST。设备令牌独立随机生成、绑定设备、服务端存哈希、可轮换/撤销；
不复用Garmin Key或看板密码。请求体、记录数与字段范围有界，忽略代理头绕过，禁止请求体/Authorization进入日志。

| 现有层 | 增量职责 |
| --- | --- |
| domain | 已实现环境schema、质量/覆盖与一致性校验；后续增加派生时间映射和只读查询 |
| storage | 新增设备/配置、环境记录/事件、时间锚点和迁移元数据；不混入Garmin原始事实表 |
| services | 验证后事务接收、批次确认、状态与查询；写事务短小，与Garmin采集使用busy_timeout/有限重试 |
| app / security | 设备POST认证/大小/频率控制；浏览器GET接口继续只读 |
| views / timeline | 下一阶段：返回有单位/配置/质量的环境序列及事件；前端按指标描述渲染，共用UTC光标 |
| backup | 已把环境表纳入备份/恢复验证；生产恢复演练仍待部署验收 |

环境接收和存储已建立，**环境曲线尚未进入实际看板**。下一阶段补环境只读查询与前端图例、单位轴、质量提示、配置变更断点；时间映射仅使用可核验锚点。
不必重做整个看板。Garmin无分期区间时，环境曲线叠加睡眠窗口/现有HR与HRV，不能编造深浅睡顺序。
注册设备时先备份和校验现有数据库，再增加环境表与索引；Garmin事实表保持独立，核验结果见报告，出现不兼容时停止而不删库重建。

## 一年数据量与2核2G权衡

每天1440条分钟记录，一年525,600条；正常约每5分钟批量上传，补传和状态分包可能增加请求数。
当前请求硬上限64KiB，固件每批最多12条记录，不能把HTTP上限乘请求数当作实际流量。
C序列化输出和接收链路已可用，样本字节数见[核验报告](../verification.md)；长期预算仍应以真实夜间数据为准。

保守规划可以先按每分钟4KiB、每分钟最多一个1KiB事件、每5分钟1KiB状态和每小时1KiB锚点估算，
约7.7MB/日、2.8GB/年JSON量级；这是较保守的预留模型，不是实测值，也不含全部SQLite/备份成本。
[核验报告](../verification.md)已有7天合成SQLite增长实测，按该负载约1.3GB/年环境库，可作为更贴近程序实现的工程参考；实机年度增长仍须观察。
20GB仍可作为单用户起点；沿用[架构磁盘预算](../architecture.md)，运行7日/30日后按实际新增字节更新全年预测。
至少留25%磁盘余量；日志、备份数量/总量上限与异机副本要在部署时落实。不能凭当前主机测试承诺全年不清理或2核2G已验收。

2核2G适合单用户这一级上传与查询；验收包含同时Garmin同步、硬件补传、夜间查询和备份，无OOM/锁死，暖查询P95<1秒。
不先升级。2核4G主要增加并发与备份的内存余量，不改善测量精度；若因存储增长不足，20→40GB比只加CPU更直接。
若保留更多原始数据、更多设备或将来分析，按监测结果扩容；第一版不引入模型训练常驻服务。
